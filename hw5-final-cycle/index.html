Final Cycle: a nightly wheel on Alphabet

Felipe Jaramillo · FINTECH 535 · GitHub Action → open_orders.json → Sanji

What this is

Every night at 10 pm Eastern a GitHub Action runs wheel_algo.py. The script reads the prices Sanji pushed into this repo and the current book, decides the next session's trade, and rewrites open_orders.json at the repo root. Sanji fills the order on Luffy and writes back positions and fills, which the next night's run reads. That closes the loop.

Tonight's decision

Why the wheel

The edge is the volatility risk premium: option prices usually imply more movement than the stock delivers. In my HW4 backtest, implied volatility was above realized volatility in about 80% of weeks on both AAPL and MP. Selling a put, and a call once assigned, collects that gap every week without having to predict direction.

The HW4 results: the wheel roughly halved volatility and raised the Sharpe ratio against buy-and-hold on both stocks. It beat buy-and-hold on the falling stock (MP) and lagged on the rising one (AAPL) because selling calls caps the upside. So the expected result live is a smoother line with a better Sharpe ratio, not a higher return in a rally.

Why Alphabet

Alphabet is the stock Sanji seeded in this repo's price_history.json (IBKR conid 208813720). It is very liquid with tight option spreads, so fills near the open are realistic.

What would prove it wrong

  • Realized volatility rising above implied for several weeks in a row: the premium I am selling is underpriced.
  • A sharp drop after a put is assigned: the HW4 failure mode, where the call has to sit above cost basis and the shares earn nothing.

Inputs → orders

Book at the closeOrder for the next session
No shares, no short optionSHT 1 put, 5DTE+, strike pct:-X
100+ shares, no short callSHT 1 call, 5DTE+, strike pct:+X, never below cost basis
A short put or call still openNothing: let it expire or be assigned. Sanji applies assignment at the close.

Strike distance X

X is half of one week's expected move, using 20-day realized volatility from price_history.json:

sigma_week = RV_20d × sqrt(7 / 365)
X          = 0.5 × sigma_week     (in percent, rounded to 0.1)

Half a weekly sigma is roughly a 30-delta option, the same target I used in HW4. Using pct instead of delta keeps orders resolvable: Sanji only needs the strike list for pct, while delta needs a chain snapshot that Robin may not have yet. When volatility rises the strike moves further out on its own.

Order details

  • Expiry 5DTE+: the nearest listed expiry at least 5 days out, the weekly wheel from HW4.
  • Market order at the open: an unfilled limit would leave the wheel idle for a week. Alphabet's spreads are tight, so the cost is small.
  • One contract: Sanji does not check buying power, so sizing is kept to one cash-secured contract.
  • IDs like googl-csp-2026-11-23 are unique per session, so a rerun the same night cannot double-fill.
  • Orders not yet processed (dated today or later) are kept; older ones are dropped since Sanji already resolved them.
  • Holidays: the session date skips weekends and market holidays (Thanksgiving, Christmas, New Year).

The GitHub Action

Modeled on the course's oi-plots.yml: same 03:00 UTC cron, same concurrency guard, same auto-commit step.

on:
  workflow_dispatch:
  schedule:
    - cron: "0 3 * * *"     # 10pm EST / 11pm EDT
concurrency: { group: nightly-orders, cancel-in-progress: true }
permissions: { contents: write }
steps:
  checkout → setup-python 3.11
  → python wheel_algo.py      (LSEG secrets passed in as env)
  → git-auto-commit: open_orders.json, hw5-final-cycle/status.json

The commit updates the site through GitHub Pages, so this page always shows the latest orders.
